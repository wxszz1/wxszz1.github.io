## 1. 模型给出了回复，还要判断能不能存

昨天回答追问后，模型已经能结合原笔记、问题和补充答案继续回复。今天补上的是把回复整理成一条独立的知识结论，保存到 `note.json`。

提示词要求模型输出单行纯文本，不要寒暄、列表和 Markdown，但程序里也得检查。最初复测时，模型替身返回 `**第二次请求超时。**`，这段加粗文本仍被当成成功结果写入，待办也移除了。只在提示词里写要求，不能保证收到的文本就符合要求。

我补了常见格式标记的拦截。修完后，缺少密钥会在创建客户端前返回；带加粗标记的结果不会写入，待办仍保留。另外还有一个普通卡片处理后不出队的问题，也一起修掉了，不然它会一直占着队首。

保存知识结论时，先检查已有 JSON 的结构，再写到同目录临时文件，最后替换原文件。只有保存成功才移除待办。导师用临时目录和模型替身复测了正常追加、空白输出、损坏 JSON 和替换失败等情况；失败场景保留原文件与待办。这些复测没有发真实模型请求，也还不能说明笔记文件和状态文件已经具有数据库式的整体事务保证。

这部分代码保存在 `4012a04`，实现和修复由我完成，复测与 Git 提交由导师协助。

## 2. 第一张 SQLite 表先服务一个具体流程

我先用 Python 自带的 `sqlite3` 写了两个脚本：一个建表、写入并提交，另一个在新进程里读回。暂时没有加 ORM，也没有直接迁移原来的 JSON 数据。

`cards` 表只放五个字段：

1. `id`：根据编号找到要回答的卡片。
2. `state`：记录还在等待回答，还是已经回答。
3. `source`：原始笔记，接续模型时需要带上。
4. `question`：追问的具体内容。
5. `answer`：用户补充的回答。

写入进程结束后，读取进程查到了同一条 `open` 记录。导师也在独立临时库里分别启动两个进程复测，读回的五个字段一致。脚本保存在 `6428db1`，样例数据库只留本机，不提交到仓库。

这里的 `state` 只是记录状态。表里有这个字段，并不会自动阻止重复回答，更新时还得使用它。

## 3. 重复回答保护放到更新条件里

今天接着写了 `answer_sqlite.py`，更新语句是：

```sql
UPDATE cards
SET answer = ?, state = ?
WHERE id = ? AND state = 'open'
```

参数里传入清理过的答案、`decided` 和卡片编号。用 `cursor.rowcount == 1` 判断这一条更新有没有实际生效。

这样第一次回答会保存答案并改变状态，再回答同一个编号，就不符合 `open` 条件了。未知编号也匹配不到记录。纯空白回答则在执行 SQL 前拦住。

本机运行后看到的几种结果：

```text
首次回答：保存成功
重复回答：卡片不存在或已回答，未修改
未知编号：卡片不存在或已回答，未修改
空白回答：答案为空
```

最终记录还是第一次保存的“第二次请求超时”，没有被后面的覆盖回答改掉。导师在临时库重新启动回答脚本复测，两次最终记录也一致。本轮提交是 `d0b42e2`。

目前验证的是这些输入和重启后的行为，还没验证异常回滚，也没有做并发写入测试。下一项先补失败回滚，再把 SQLite 接回现有模型流程。
