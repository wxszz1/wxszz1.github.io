今天一边继续看 Python 后端，一边问了几个关于 Agent 的概念。先把容易混的地方记下来，后面还要通过代码去理解。

## 1. 文件搬了位置，路径也要跟着检查

我把项目里的文件放到了 `src` 目录下面，数据文件又放进了 `src/data`。这样整理完目录，不代表原来的代码就一定能正常运行。

比如原来这行：

```python
DATA_FILE = Path(__file__).with_name("articles.json")
```

它找的是和当前代码文件放在一起的 `articles.json`。如果代码在 `src/api.py`，它指向的就是 `src/articles.json`，不会自己去 `data` 目录里面找。

现在接口文件里写成了：

```python
DATA_FILE = Path(__file__).parent / "data" / "articles.json"
```

`__file__` 表示当前模块文件的路径，`parent` 取它所在的目录，再往下接 `data` 和文件名。这样数据位置是根据代码文件来确定的。

还有一种写法是直接写 `"data/articles.json"`，它通常是相对于程序启动时的工作目录。启动位置一变，找到的地方也可能变，所以不能只看这个字符串像不像正确路径。

导入也要一起检查。把文件放进 `src` 后，启动时可以用下面这种方式告诉 Uvicorn 去哪里找应用：

```powershell
python -m uvicorn api:app --app-dir src --reload
```

这里的 `api:app` 是加载 `api` 模块里的 `app`，`--app-dir src` 指定查找应用的目录。实际运行时还要使用项目对应的 Python 环境。路径写法调整了，也还需要启动验证，不能只看代码就说整个项目已经跑通。

## 2. 更新文章时，查重不能把自己算进去

接下来要补的是修改文章标题和链接。今天老师给了业务函数的示例，我还没有完成这部分实现和测试，先记一下校验思路。

顺序是先找到要修改的文章，再检查新数据，最后才真正改动。

检查链接是否重复时，有这样一个条件：

```python
article["id"] != article_id and article["url"] == url
```

前半句是排除正在修改的文章。因为只修改标题、保留原链接也是正常操作，如果连自己都参与查重，就会把原来的链接判断成重复。

还要考虑文章不存在、标题只有空格、链接和另一篇文章重复这些情况。校验失败时，不应该先把原数据改掉。更新标题和链接，也不需要重新生成 ID，原来的已读状态应该保留。

## 3. Skill不等于另外造了一个Agent

今天让 AI 帮我做了一个“总教师”技能，用来统一学习路线，再安排具体的小课。

后来我追问它到底靠什么实现，才把这件事说清楚：目前主要是教学规则、参考资料和学习记录文件，执行时借用现有工具。并没有因为起了“总教师”这个名字，就另外开发出一套独立运行的教师系统。

Skill 可以理解为可复用的做事方法。简单的 Skill 主要是提示词和说明，复杂一点也可以带脚本、模板和资料。它告诉执行者怎么做，但文件放在那里，并不意味着任务已经开始执行。

## 4. Agent、Harness和Bot不是三个互斥的东西

我最开始的问题是：Agent 是不是比 Skill 多几个程序来监督调用？后来发现不能只按程序数量来区分。

Agent 的重点在于根据目标和执行结果，决定接下来做什么。例如读取学习记录之后，判断应该复习、练习，还是进入下一课。

Harness 是支撑这个过程的运行框架。它可以把信息交给模型，执行模型选出的工具调用，再把结果传回去，也可以管理状态、限制、暂停和恢复。它通常是 Agent 系统的一部分，不是旁边又站了一个监督机器人。

可以先用下面这个过程帮助理解：

```text
提供目标和上下文
    → 模型决定下一步
    → 程序执行工具调用
    → 把执行结果交回模型
    → 继续、等待，或者结束
```

Bot 则是“机器人服务”的叫法。固定收到一句话就回复一句话，也可以叫 Bot；背后接了模型和工具、能推进任务的，也可以叫 Bot。

所以 Bot 不能直接等同于前端，Bot 和 Agent 也不一定是二选一。同一个产品可以既是 Bot，又采用 Agent 的工作方式。这些词在不同项目里用法也会有差别，还是得看实际能做什么。

## 5. 产品做得好，不一定是发明了新概念

聊到 Grok Bot 时，我一直想问的是：既然它也是 Agent，为什么还会引起关注？

这里可以从产品角度想一下。用户不一定关心底层叫 Agent 还是 Harness，更多是看入口是否方便、工具有没有接好、任务能否真的完成。

把已有能力组合成一个能直接使用的产品，也有价值。不过这只是解释产品吸引力的一种思路，不能直接当成它实际走红原因的结论。真正使用时，还要看成功率、成本，以及失败以后能不能恢复。
