2026.11.19学习笔记（SQLite 回滚、追问接续和 JSON 订单去重）

发表于2026-11-19|更新于2026-11-20|学习笔记

今天在学习笔记助手里试了两个场景：回答写到一半失败，退出后再从数据库找回已回答的卡片。下午还重跑了一个把 JSON 订单拆开入库的课程实验。

1. UPDATE 执行了，提交前出错怎么办

我在 UPDATE 后、commit() 前主动抛了一个异常，模拟还没提交就出错。异常分支调用 rollback()，打印失败提示后直接返回。要是还往下检查 rowcount，即使刚才更新过一行，也不能用它判断最后存没存成功。

回滚后我用同一个连接马上查数据库，卡片还是 open，答案也是空的。这样在程序退出前就能确认改动已撤回。关掉故障开关，再提交一次答案，另开一个读取进程就能查到 decided 和重试后的答案。

2. 从 SQLite 读卡片，再交给模型

我写了一个独立入口，按编号查卡片，读完就关闭连接。只有卡片已经回答，而且原笔记、追问、答案三项都齐全，才把它们交给接续函数。

这轮用模型替身来数调用次数和核对入参。重启后读取已回答卡片，调用一次，三段内容都来自数据库。未知编号和还没回答的卡片都是零次调用。模拟模型超时后，同一张卡片还能拿原答案重试，复测前后的数据库文件也一致。

调试时碰到一个小问题，运行脚本后在 PyCharm 里没看到新卡片。导师直接在项目目录运行写入脚本，查到了新增记录。这里要注意 demo.db 用的是相对路径，运行配置的工作目录和数据库面板看的文件需要对上。表格也可以刷新后再看。

回滚和接续由我实现和实跑，导师复测并协助保存本地提交 2f78628 和 2cdf10b。这次验证的是独立脚本里的模型接续，完整菜单和待办队列还没迁到 SQLite。

3. 一条 JSON 订单拆成了几条记录

课程实验里，我按步骤重新跑了提供的示例。订单里的商品是个列表，入库时拆成一条订单主记录和两条商品明细。程序写出 CSV、写入 MySQL，再在 file_monitor 登记这个文件已经处理。

第一次跑完，订单、明细、文件处理记录分别是 1、2、1。第二次运行，待处理列表为空，三张表还是 1、2、1。第一次看写入有没有完成，第二次看同一个文件会不会被重复导入。这组数字来自我对示例的实跑，实验脚本和操作材料由 AI 协助准备。

我还对照了参考截图。它展示的是多个订单 ID，我这次用单条示例验证了拆分、写入和文件去重。核对实验时，命令行长什么样和数据实际变了什么，最好分开检查。
